## 与 4K 的关系

2048 和 4K 不是简单线性缩放：

- 4K 顶层第一项在 `(1986,1100)`；
- 2048 顶层第一项在 `(1200,427)`；
- 直接按分辨率比例换算对不上，说明 UI 布局/锚点随窗口模式变化。

因此不能把 4K 的 `ui_layout` 直接用于 2048，也不能把 2048 数据写进原来的
2560 `ui_layout`。

## 第二座城复测：偏移不稳定

又在一座己方城 **小沛** 上左键打开指令菜单：

```text
小沛顶层第一项中心 ≈ (1013,452)
城池格子中心 ≈ (1015,355)
城池名字中心 ≈ (1055,270)
```

相对偏移：

```text
相对格子中心 ≈ (-2,97)
相对名字中心 ≈ (-42,182)
```

而南皮是：

```text
相对格子中心 ≈ (+95,37)
相对名字中心 ≈ (+50,122)
```

两座城的相对偏移差异很大，**固定“城池锚点 + 固定偏移”的模型不成立**。
最可能的原因是：

- 菜单按**左键点击时的鼠标位置**定位；
- 或菜单会为避开屏幕边缘而翻转/平移；
- 两座城点击时点的位置不同（名字/格子）。

因此 `ActionMenuExecutor` 现在使用的“投影城池点 + 固定菜单偏移”不可靠，
需要先确认真实定位规则。

## 边界

- 目前只有两座城、各一次样本；
- 没验证靠近屏幕边缘时菜单是否自动翻转/偏移；
- 没确认锚点到底取城池格子中心还是名字文本框；
- 生产 `ui_layout` / `offsets` 没有修改。

## 菜单定位器原型

新增研究工具 [locate_menu.py](tools/locate_menu.py)：从截图中按颜色阈值检测
深色菜单按钮和 teal 子菜单外框，返回候选矩形。它已能在 2048 截图上找到：

```text
顶层按钮框约 65×25
子菜单外框约 (1245,416)-(1354,658)
item_height 约 34
```

工具依赖 Pillow/numpy（使用 DSH bundled Python），不进入生产包、不参与
`428 passed` 的核心测试；下一步应把“检测到的菜单矩形”转换成点击坐标。

## LiveMenuRunner 原型

新增 [live_menu_runner.py](tools/live_menu_runner.py)：从实时窗口截图或已有
截图检测菜单，并输出可直接喂给 `ActionMenuExecutor` 的 `MenuGeometry`。

在 2048 截图上的结果：

```text
顶层：left=1171 top=414 right=1236 bottom=609 item_height=34 count=6
都市子菜单：left=1245 top=416 right=1354 bottom=658 item_height=34 count=7
```

它不发送输入，只负责“截图 -> MenuGeometry”；输入仍由
`ActionMenuExecutor` 的 locator 路径完成。依赖 Pillow/numpy（bundled
Python），尚未进入生产运行时。

## 一次误点与防护

第一次尝试自动点击时，截图里其实没有菜单（切回游戏时菜单已关闭），
检测器把其他深色 UI 误判成菜单并点击，结果只是**选中了南皮城池**，没有
执行任何指令。

随后给 `live_menu_runner.py` 加了硬性防护：

- 顶层菜单必须是 5~7 项、`item_height` 25~45、宽度 40~120；
- 子菜单必须是 3~10 项、`item_height` 25~45、宽度 55~180；
- 中心必须靠近左键点击点。

用误点截图验证：现在顶层和子菜单都返回 `null`，不会再误点。

## 自动检测 + 点击「都市」成功

在受控测试中，把聊天窗口移开（不最小化）、保持游戏前台，用户左键南皮后，
`live_menu_runner` 截图检测并真实点击了一次「都市」：

```text
顶层检测：left=991 top=563 right=1056 bottom=758
          item_height=34 count=6
点击「都市」：client=(1023,580) screen=(1084,857)

点击后子菜单：left=1065 top=566 right=1174 bottom=807
              item_height=34 count=7
```

只点击了「都市」，**没有点击任何子菜单指令**。截图确认
`開發/吸收合併/徵兵/生產兵裝/巡察/商人/研究技巧` 正常展开。

这验证了：

- 截图检测 -> `MenuGeometry` -> `ActionMenuExecutor` 的 locator 路径可行；
- 菜单位置不需要固定 `ui_layout` 偏移；
- 点击后可以再次截图检测子菜单。

## 更正：左键打开一级菜单

2026-10-23 用户明确更正：

- **左键单击自己的城池** -> 一级指令菜单（都市/軍事/人材/外交/計略/君主）；
- 右键 -> 情报菜单（詳細情報/所屬武將/勢力情報…）。

`ActionMenuExecutor.open_city_menu()` 原本就使用单次 `click()`（左键），
所以代码方向是对的；之前报告里的“右键打开指令菜单”文字已更正。

## 巡察面板确认

用户手动点击「巡察」后，巡察面板如预期出现。这说明：

```text
左键城池 -> 都市 -> 巡察
```

这条菜单路径是真实可用的；不是只有截图/检测层面成立。具体巡察动作的
确认/执行仍未由自动化完成。

## 巡察面板截图

用户在自动点击「都市」、再点「巡察」后确认面板出现。当前 2048 截图显示：

```text
标题：巡察
执行武将：張燕 / 程遠志 / 眭固
治安：73 -> 82
```

底部按钮近似坐标（客户区）：

```text

```

还没有点击「決定」；这是下一步真正产生动作效果的入口。

## 手动点击「決定」后的后置条件验证

用户手动点击「決定」后，读取游戏状态确认：

```text
南皮 city[3], force[5]
gold     8785 -> 8685   (-100)
security   73 -> 82     (+9)
force AP  255 -> 235    (-20)
```

结果 **confirmed**：金币、治安、行动力三项都符合巡察的预期后置条件。

这也说明菜单链路不是“只点开了界面”：

```text
左键城池 -> 都市 -> 巡察 -> 決定
```

真实改变了游戏状态。

## 全自动巡察尝试（未执行成功）

第一次尝试自动执行完整“都市→巡察→決定”时，顶层检测误把其他行也算进去，
返回 `count=7`，点击链没有命中正确项。结果：

- 金币仍为 `8685`；
- 治安仍为 `82`；
- force AP 仍为 `235`；
- 没有任何新动作被执行。

随后把顶层菜单约束收紧为**必须正好 6 项**（都市/軍事/人材/外交/計略/君主），
误检的 `count=7` 现在会直接返回 `null`，不再进入点击。
