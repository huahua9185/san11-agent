# REA：D3D 视图/投影矩阵排查（2026-10-23）

## 已确认

**修正**：IDirect3DDevice9 的 `SetTransform` 在 vtable `+0xB0`（state, pMatrix），
不是之前误用的 `+0x110`。重新扫描 `.text`（VA `0x401000`，大小 `0x34CEF1`）
后，共 4 处 `call dword ptr [reg+0xb0]`：

| 地址 | state | 矩阵来源 |
|---|---:|---|
| `0x403912` | `0x100` | 调用方参数 |
| `0x40BB57` | `0x100` | `FUN_004437D0` |
| `0x40BD10` | `0x100` | 栈上矩阵 |
| `0x421C84` | `0x100` | `FUN_004437D0` |

`0x100` 是 `D3DTS_WORLD`。**四处全部是 WORLD 变换，没有一处设置
`D3DTS_VIEW(2)` 或 `D3DTS_PROJECTION(3)`**。因此固定功能管线的 view/projection
不是在这几处设置的；游戏更可能用 shader/effect 常量传矩阵。

`FUN_0043D270` 里的 `+0x114` 调用不是 `GetTransform`；按 vtable 顺序更像另一个
接口槽（先前误标为 GetTransform）。它同时设置多个渲染状态，仍不能证明是相机。

## 重要否定结果

检查过的候选：

```text
0x794850
0x794894
```

不是 4×4 float 矩阵，而是 `.rdata` 里的资源/格式字符串附近数据（例如
`D3DFMT_DXT4`、`D3DFMT_DXT5`）。不能把 `push 0x794894` 当成矩阵上传。

另外，`+0x178` 的 42 处调用也不一定是“上传 shader 常量”；按 D3D9 顺序它更
接近 `GetVertexShaderConstantF` 或引擎包装接口。需要函数级确认，不能继续按
“42 个上传点”这个假设推进。

## 当前判断

- 地图是 3D 渲染；`camera.offset_x/offset_y/zoom_level` 这组二维字段前提需要
  重新审视；
- 固定功能 `SetTransform` 只用于 WORLD，view/projection 很可能通过
  shader/effect 常量或引擎包装函数设置；
- 下一步应分析 `FUN_0044D1F0` 这类包装函数，以及调用它的 shader/effect
  初始化路径，而不是继续猜固定功能 vtable；
- 仅凭 vtable 偏移和常量地址猜矩阵已经证明会产生假线索。

## 下一步

1. 分析 `FUN_0044D1F0`（`0x44D1F0`）：它委托到 `[obj+0x114]`，需要确认
   这是哪个接口/方法；
2. 跟踪 `FUN_0044B470` 等 shader/effect 初始化函数的首参对象类型和常量源；
3. 找到 view/projection 后，用已知城市点做投影验证，再决定是否还需要
   `camera.offset_x/y/zoom_level`；
4. 不要把二维等距公式继续硬套到 3D 地图上。
