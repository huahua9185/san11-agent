# REA：D3D 视图/投影矩阵初步排查（2026-10-23）

## 结论

**已确认（静态扫描）**：游戏使用 Direct3D 9，设备指针全局为
`DAT_06ed6f74`。对 `.text`（VA `0x401000`，大小 `0x34CEF1`）扫描 COM
vtable 调用：

| vtable 偏移 | 次数 | 暂定语义 |
|---|---:|---|
| `+0xE4` | 215 | 渲染状态相关 |
| `+0x10C` | 182 | 渲染/资源相关 |
| `+0x178` | 42 | 疑似 shader 常量上传 |
| `+0x170` | 20 | 疑似 shader 相关 |
| `+0x15C` | 17 | 渲染状态相关 |
| `+0x114` | 1 | `GetTransform` 样式调用，位于 `0x43D32E` |

**没有**在 `.text` 里找到直接的
`call dword ptr [reg+0x110]`（IDirect3DDevice9::SetTransform）调用。这更像
两种情况之一：

1. 游戏通过引擎自己的包装函数设置矩阵；
2. 游戏主要使用 shader，矩阵通过常量上传，而不是固定功能 SetTransform。

`FUN_0043D270`（`0x43D270`）包含唯一的 `+0x114` 调用，同时设置多个渲染
状态；它目前只能标为“可能读取某个变换矩阵”，不能证明是 3D 相机。

## 重要否定结果

我检查了两个看起来像矩阵全局的地址：

```text
0x794850
0x794894
```

它们不是 4x4 float 矩阵，而是 `.rdata` 里的资源/格式字符串（例如
`D3DFMT_DXT4`、`D3DFMT_DXT5` 等）附近的数据。因此不能把
`push 0x794894` 当成矩阵上传。

这说明仅靠“扫描 vtable 调用 + 猜常量地址”不足以定位视图/投影矩阵。

## 当前判断

- 地图是 3D 渲染；`camera.offset_x/offset_y/zoom_level` 这组二维字段的
  前提本身需要重新审视；
- 真正需要的是 D3D 的 **view/projection matrix** 或游戏自己的
  world-to-screen 函数；
- 下一步应聚焦在 `+0x178` 的 42 个 shader 常量上传点，尤其是一次上传
  4 个 float4（一个矩阵）且数据源来自全局/对象字段的调用；
- 仅凭 `.text` 的调用模式还不够，需要结合函数伪代码和矩阵数据布局确认。

## 下一步

1. 对 `0x44B6xx`、`0x405xxx`、`0x412xxx` 等 shader 常量上传簇做函数级
   分析，找出一次上传 4 个 float4 的代码；
2. 跟踪这些常量的数据源（栈/全局/对象字段），判断哪个是 view、哪个是
   projection；
3. 找到矩阵后，先用它与已知城市点做投影验证，再决定是否还需要
   `camera.offset_x/y/zoom_level`；
4. 不要把二维等距公式继续硬套到 3D 地图上。
