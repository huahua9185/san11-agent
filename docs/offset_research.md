> 所有数值均来自下方列出的开源资料原文，**没有任何一项是本项目自行推算或猜测填入的**。
> 无法从资料中直接找到、又不愿意猜测的字段，一律在 `offsets/pk_1.1_cn.json` 中标为 `"unknown": true`，并在本文"未解决问题"一节列出，需要你确认或提供。

## 2. 版本适配问题（重要，尚未解决）

- 311MemoryResearch **全仓库没有任何地方**写明这些地址对应的 `san11pk.exe` 具体版本号、补丁号、文件大小或哈希值。全文检索"版本/补丁/威力加强/正式版/steam/校验/MD5"均无有意义命中。
- `SirePluginDemo/MemoryManager.cs` 硬编码 `EXE_OFFSET = 0x400000`，隐含假设 exe 的 `ImageBase = 0x00400000` 且不开 ASLR，但代码里**没有**做 PE 头校验或版本探测，作者自己的工具也是"假设它是对的"直接用。
- Steam 版兼容性完全未提及。
- **结论**：本项目暂时只能把这套偏移当作"针对某个未知具体版本/补丁号的威力加强版单机版"的候选值，标签定为 `pk_1.1_cn`（沿用规格文档里的示例命名，**不代表已确认版本号是 1.1**）。真正的版本号需要你提供，或者由你运行游戏后我们一起用后文"启动校验"环节反推确认。

## 3. 核心发现：数据基址与派生结构体

资料中给出了一份手工整理表（`内存资料/地址资料.txt` 第 1497~1846 行附近），描述了一个"全局数据基址"，以及武将/城市/势力/军团/部队五张表相对该基址的偏移、结构体大小、数组数量：

```
GAME_DATA_BASE   起始地址(某次运行观测值) = 0x07201958   大小未注明
General(武将)    = GAME_DATA_BASE + 0xC0BC     结构体大小 0x190   数量 0x44C (1100)
City(都市)       = GAME_DATA_BASE + 0x1D8      结构体大小 0x248   数量 0x2A  (42)
Faction(势力)    = GAME_DATA_BASE + 0x7AF8     结构体大小 0x12C   数量 0x2A  (42)
Force(军团)      = GAME_DATA_BASE + 0xB20C     结构体大小 0x50    数量 0x2A  (42)
Troop(部队)      = GAME_DATA_BASE + 0x169630   结构体大小 0xF4    数量 0x44C (1100)  ⚠ 见下方"数值矛盾"
```

武将（1100）/都市（42）/势力（42）三个数组的加法经核对与原文给出的绝对地址完全吻合，可信度较高。

**⚠ 数值矛盾**：Troop 一行按公式算出的地址应为 `0x0736AF88`，但原文档独立写的是 `0x0736B088`，两者相差 `0x100`（256 字节）。无法判断是原作者笔误还是公式本身在这一行有额外偏移，**没有做任何"修正"，两个候选值都原样保留在 offsets 文件里**，需要你实测确认。

### ⚠ 最大的未解决问题：GAME_DATA_BASE 本身怎么找

`0x07201958` 是资料原文里的一个**具体数值**，但资料**完全没有说明这个数值是怎么来的**：

- 如果它是编译期固定的静态/全局数据地址（即 `模块基址 + 固定RVA` 能直接算出，且这块内存本身就是数据存放处），那么理论上可以推出 RVA = `0x07201958 - 0x00400000` = `0x06E01958`（约 110MB）。但这个 RVA 大得不寻常，一个典型 PE 文件的 `.data`/`.bss` 段不太可能有 110MB，这让"它是静态地址"的假设显得可疑。
- 更常见的可能性是：`0x07201958` 其实是**某次运行时，游戏在堆上分配的数据块地址**，而真正稳定的是"模块基址 + 一个较小的固定 RVA，处存放着一个指向这块堆内存的指针"（典型 Cheat Engine "指针"扫描结果）。如果是这种情况，那么 `0x07201958` 这个值本身**每次重启游戏都会变**，现在资料里记录的绝对地址整体作废，必须先做一次指针扫描重新定位。

资料里完全没有给出这个"锚点"本身的定位方法（既没有 RVA，也没有指针链）。**这是我不愿意猜测、必须问你的核心问题**，详见下方"需要你确认的问题"第 1 条。

## 4. 各结构体明细与可信度

### 4.1 武将 (General) — 可信度：高
两份独立文件交叉印证：`地址资料.txt` 的整理表 与 `内存资料/整理/Func-情报03-获取武将信息【未】.txt` 里对函数 `004C8720`（游戏内部"获取武将信息"命令分发函数）的反汇编注释，多个字段（所在 `+0x9C`、身份 `+0xA0`、官职 `+0xA4`、忠诚度 `+0xAC`、功勋 `+0xAE`、体力 `+0x128`、健康程度 `+0x15C`）完全吻合。

### 4.2 城池 (City) — 核心字段可信度：高，坐标/所属势力：中
`地址资料.txt` 整理表 与 `内存资料/整理/Func-情报02-获取城市信息.txt`（函数 `004C0C30` 反汇编）交叉印证了兵力(`+0x40`)/钱(`+0x44`)/粮(`+0x48`)等字段。
**缺口**：城池"自身所属势力ID"和"城池地图坐标(x,y)"在整理表里找不到直接字段偏移——资料显示这两项是通过虚表函数调用取得的，且"城市指针→设施(Facility)指针"这一跳的偏移常量本身也没有给出（只有函数地址 `0047c4c0`）。已在 offsets 文件中标为 unknown。

### 4.3 部队 (Troop) — 可信度：高（单一来源，但内部字段被独立反汇编文件部分印证）
`地址资料.txt` 直接给出主将ID(`+0x0C`)、兵力(`+0x18`)、坐标X/Y(`+0x3C`/`+0x3E`)、所属势力(`+0x44`)等核心字段；`内存资料/函数[部队攻击].txt` 的反汇编独立印证了兵种(`+0xA8`)、显示属性(`+0xC6~0xCB`)等字段。基址本身见上方"数值矛盾"。

### 4.4 势力 (Faction) — 可信度：中高（附带找到，不在你原始需求范围但 general/city 会引用）
君主ID(`+0x04`)、军师ID(`+0x08`)、47个势力好感度表(`+0x0C`起)、玩家序号(`+0x60`，用于判断"哪个势力是我")、科技研究(`+0x9C`)、技巧点(`+0xA2`)。单一来源，未交叉验证。

### 4.5 全局参数 / 回合 / 日期 / 阶段 — 可信度：中，且有明显缺口
`地址资料.txt` 给出剧本编号(`+0x04`)、开始年/月/日(`+0x08/0x0C/0x10`)、皇帝ID(`+0x14`)、难度(`+0x20`)、战死设定(`+0x24`)、**当前旬数**(`+0x5C`，"旬"=10天，是最接近"回合数"的字段)。
`+0x28~+0x58` 之间完全没有记录，原作者自己标注"共 0x?? 个字节"表示连结构体总大小都不确定。

**当前年/月/日**：资料里**没有找到**可以直接读取的字段偏移，只找到三个函数地址（`004824B0`/`004824F0`/`00482530`，推测分别返回当前年/月/日），但没有给出内部换算公式。可选方案：(a) 用"开始年月日 + 当前旬数 × 10天"自行换算并做合理性检查；(b) 未来考虑 hook/调用这几个函数取值（复杂度更高，M1 不做）。

**游戏阶段（内政/战略/战斗等）标志位**：全仓库关键词检索（游戏阶段/内政阶段/战略阶段等）**完全没有命中**，即完全未找到。

## 5. 需要你确认的问题（不猜测，明确列出）

1. **GAME_DATA_BASE 锚点的定位方法未知**——是否有你手头的其它资料/工具（比如某个能跑起来的 CE 表、SCP 插件源码）能提供"模块基址 → GAME_DATA_BASE"的指针链？或者你打算之后我们一起对着运行中的游戏做指针扫描重新定位？在锚点问题解决前，`--pid`/实时进程模式在代码里会显式报错退出，不会静默用一个可能失效的绝对地址。
2. **Troop 基址的 `0x100` 差值**（`0x0736AF88` vs `0x0736B088`）到底哪个对，需要你用实际内存实测两个候选地址来确认。
3. **城池所属势力ID / 城池地图坐标**的直接字段偏移未找到，需要进一步逆向或你提供。
4. **当前年/月/日**没有直接字段，需要你确认是否接受"开始日期+旬数换算"的方案，或者你有更好的资料来源。
5. **游戏阶段标志位**完全没有线索，是 M1 里最大的空白，需要你提供或者我们后续专门做内存搜索（比如切换内政/战略界面时对比内存快照差异）来定位。
6. **具体游戏版本号/补丁号**未知，需要你告诉我你实际运行的版本（在"游戏 -> 关于"或 exe 属性里通常能看到），后续用于给 offsets 文件正确命名和做启动校验。
7. `内存资料/整理/Func-情报03-获取武将信息【未】.txt` 文件名带"【未】"（可能表示"未完成"），该文件内容仅作为交叉印证使用，如果后续字段对不上请优先怀疑这份资料。

## 6. 本项目的应对策略

鉴于以上不确定性，`offsets/pk_1.1_cn.json` 中：
- 已找到且交叉验证过的字段：填入数值，标注 `"confidence": "high"` 或 `"medium"`，并注明来源文件。
- 找不到的字段：`"offset": null, "unknown": true`，并写明原因，**perception.py 解析时会跳过这些字段而不是猜测**。
- 启动校验逻辑（`san11agent/validate.py`）在锚点解析方式确认之前，遇到实时进程模式会直接抛出明确异常并退出，不会静默使用未经验证的地址——这是刻意的设计，符合"遇到不确定的地址直接问用户，不要猜测填值"的要求。
