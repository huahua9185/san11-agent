## 2. 版本适配问题

- 311MemoryResearch **全仓库没有任何地方**写明这些地址对应的 `san11pk.exe` 具体版本号、补丁号、文件大小或哈希值。全文检索"版本/补丁/威力加强/正式版/steam/校验/MD5"均无有意义命中。
- `SirePluginDemo/MemoryManager.cs` 硬编码 `EXE_OFFSET = 0x400000`，隐含假设 exe 的 `ImageBase = 0x00400000` 且不开 ASLR，但代码里**没有**做 PE 头校验或版本探测，作者自己的工具也是"假设它是对的"直接用。
- Steam 版兼容性完全未提及。
- **结论（2026-08-18 之前）**：本项目暂时只能把这套偏移当作"针对某个未知具体版本/补丁号的威力加强版单机版"的候选值，标签定为 `pk_1.1_cn`（沿用规格文档里的示例命名，**不代表已确认版本号是 1.1**）。
- **2026-08-18 更新**：已实机确认真实进程是 **Steam 繁体中文版 `San11WPK.exe`**（而不是本节和 offsets 文件早先假设的简体版 `san11pk.exe`），具体文件身份信息、以及"两个版本是否兼容"的实测结论见第7节。简要结论：**核心数据结构偏移在繁中 Steam 版上验证通过**，已知的真正差异只有文本编码（简体 GBK vs 繁体 cp950/Big5，见 7.4）。

## 3. 核心发现：数据基址与派生结构体

资料中给出了一份手工整理表（`内存资料/地址资料.txt` 第 1497~1846 行附近），描述了一个"全局数据基址"，以及武将/城市/势力/军团/部队五张表相对该基址的偏移、结构体大小、数组数量：

```
GAME_DATA_BASE   起始地址(某次运行观测值) = 0x07201958   大小未注明
General(武将)    = GAME_DATA_BASE + 0xC0BC     结构体大小 0x190   数量 0x44C (1100)
City(都市)       = GAME_DATA_BASE + 0x1D8      结构体大小 0x248   数量 0x2A  (42)
Faction(势力)    = GAME_DATA_BASE + 0x7AF8     结构体大小 0x12C   数量 0x2A  (42)
Force(军团)      = GAME_DATA_BASE + 0xB20C     结构体大小 0x50    数量 0x2A  (42)
Troop(部队)      = GAME_DATA_BASE + 0x169630   结构体大小 0xF4    数量 0x44C (1100)  ⚠ 见下方"数值矛盾"
```

武将（1100）/都市（42）/势力（42）三个数组的加法经核对与原文给出的绝对地址完全吻合，可信度较高。

**⚠ 数值矛盾**：Troop 一行按公式算出的地址应为 `0x0736AF88`，但原文档独立写的是 `0x0736B088`，两者相差 `0x100`（256 字节）。无法判断是原作者笔误还是公式本身在这一行有额外偏移，**没有做任何"修正"，两个候选值都原样保留在 offsets 文件里**，需要你实测确认（2026-08-18 未做，见 7.6）。

### GAME_DATA_BASE 本身怎么找（2026-08-18 已解决，见第7节）

`0x07201958` 是资料原文里的一个**具体数值**，但资料**完全没有说明这个数值是怎么来的**：

- 如果它是编译期固定的静态/全局数据地址（即 `模块基址 + 固定RVA` 能直接算出，且这块内存本身就是数据存放处），那么理论上可以推出 RVA = `0x07201958 - 0x00400000` = `0x06E01958`（约 110MB）。这个 RVA 看起来大得不寻常，一度让"它是静态地址"的假设显得可疑——**这个疑虑已在 2026-08-18 的实机验证中解除，见 7.3**。
- 另一种可能性是：`0x07201958` 其实是**某次运行时，游戏在堆上分配的数据块地址**，而真正稳定的是"模块基址 + 一个较小的固定 RVA，处存放着一个指向这块堆内存的指针"（典型 Cheat Engine "指针"扫描结果）。如果是这种情况，那么 `0x07201958` 这个值本身**每次重启游戏都会变**。**2026-08-18 的单次验证结果更支持"静态地址"假说，但尚未做重启持久性确认，不能完全排除这个可能性，见 7.3/7.6。**

## 4. 各结构体明细与可信度

### 4.1 武将 (General) — 可信度：高
两份独立文件交叉印证：`地址资料.txt` 的整理表 与 `内存资料/整理/Func-情报03-获取武将信息【未】.txt` 里对函数 `004C8720`（游戏内部"获取武将信息"命令分发函数）的反汇编注释，多个字段（所在 `+0x9C`、身份 `+0xA0`、官职 `+0xA4`、忠诚度 `+0xAC`、功勋 `+0xAE`、体力 `+0x128`、健康程度 `+0x15C`）完全吻合。**2026-08-18 更新**：`name` 字段的偏移/大小本身经实机验证正确，但内部还有姓/名/字三段子结构，现有解析代码只读出"姓"，见 7.5。

### 4.2 城池 (City) — 核心字段可信度：高，坐标/所属势力：中
`地址资料.txt` 整理表 与 `内存资料/整理/Func-情报02-获取城市信息.txt`（函数 `004C0C30` 反汇编）交叉印证了兵力(`+0x40`)/钱(`+0x44`)/粮(`+0x48`)等字段。
**缺口**：城池"自身所属势力ID"和"城池地图坐标(x,y)"在整理表里找不到直接字段偏移——资料显示这两项是通过虚表函数调用取得的，且"城市指针→设施(Facility)指针"这一跳的偏移常量本身也没有给出（只有函数地址 `0047c4c0`）。已在 offsets 文件中标为 unknown。**2026-08-18 更新**：`name` 字段经实机验证，偏移/大小正确，实际文本编码应为 cp950(Big5) 而非 GBK，见 7.4。

### 4.3 部队 (Troop) — 可信度：高（单一来源，但内部字段被独立反汇编文件部分印证）
`地址资料.txt` 直接给出主将ID(`+0x0C`)、兵力(`+0x18`)、坐标X/Y(`+0x3C`/`+0x3E`)、所属势力(`+0x44`)等核心字段；`内存资料/函数[部队攻击].txt` 的反汇编独立印证了兵种(`+0xA8`)、显示属性(`+0xC6~0xCB`)等字段。基址本身见上方"数值矛盾"，2026-08-18 未做二选一验证（见 7.6）。

### 4.4 势力 (Faction) — 可信度：中高（附带找到，不在你原始需求范围但 general/city 会引用）
君主ID(`+0x04`)、军师ID(`+0x08`)、47个势力好感度表(`+0x0C`起)、玩家序号(`+0x60`，用于判断"哪个势力是我")、科技研究(`+0x9C`)、技巧点(`+0xA2`)。单一来源，未交叉验证。

### 4.5 全局参数 / 回合 / 日期 / 阶段 — 可信度：中，且有明显缺口
`地址资料.txt` 给出剧本编号(`+0x04`)、开始年/月/日(`+0x08/0x0C/0x10`)、皇帝ID(`+0x14`)、难度(`+0x20`)、战死设定(`+0x24`)、**当前旬数**(`+0x5C`，"旬"=10天，是最接近"回合数"的字段)。
`+0x28~+0x58` 之间完全没有记录，原作者自己标注"共 0x?? 个字节"表示连结构体总大小都不确定。

**当前年/月/日**：资料里**没有找到**可以直接读取的字段偏移，只找到三个函数地址（`004824B0`/`004824F0`/`00482530`，推测分别返回当前年/月/日），但没有给出内部换算公式。可选方案：(a) 用"开始年月日 + 当前旬数 × 10天"自行换算并做合理性检查；(b) 未来考虑 hook/调用这几个函数取值（复杂度更高，M1 不做）。

**游戏阶段（内政/战略/战斗等）标志位**：全仓库关键词检索（游戏阶段/内政阶段/战略阶段等）**完全没有命中**，即完全未找到。2026-08-18 未做界面切换对比（需要键鼠操作，本次只读勘察未做，见 7.6）。

  SHA256 `F2A304B118E72673F4A788B1E87322FA891FF57218A8B89E671D4F8CB6ACA041`，

### 7.2 ProcessMemoryReader 真实进程读取路径——M1 写完后首次实机跑通

`san11agent/memory.py` 的 `find_pid_by_process_name()` + `ProcessMemoryReader`
是 M1 写的、此前完全没有在真实进程上跑过的代码路径。这次实测：

- 非管理员权限下，`OpenProcess(PROCESS_QUERY_INFORMATION | PROCESS_VM_READ)` +
  `ReadProcessMemory` **直接成功**，没有遇到权限问题。
- `module_base` 读回 `0x00400000`，与 offsets 文件里 `assumed_image_base`
  一致（该 exe 没有开 ASLR，符合老游戏的典型情况）。
- 读到的 `module_base` 处前两字节是 `MZ`（PE 文件头标志），确认基址读取正确。
- **没有发现代码 bug**，这条路径按设计正常工作，不需要改动 `memory.py`
  本身的读取逻辑。

### 7.3 GAME_DATA_BASE 锚点验证（解决全局关键路径 P0 阻塞）

用 `probe-anchor` 工具测试了两种对 `0x07201958` 的解释：

| 候选 | 解析方式 | GAME_DATA_BASE | 结果 |
|---|---|---|---|
| 把 `0x07201958` 当作 RVA（`module_base + 0x07201958`） | static_rva | `0x07601958` | **未通过**：剧本编号=0、开局年份=0，全部超出合理范围 |
| 把 `0x07201958` 当作绝对地址（`module_base=0x00400000` 时对应 RVA=`0x06E01958`） | static_rva，rva=`0x06E01958` | `0x07201958` | **通过**：武将数=1100、城池数=42、势力数=42，与预期精确相等；剧本编号=7、开局年份=251-1-1，均在合理范围 |

第二种解释验证通过，已把 `offsets/pk_1.1_cn.json` → `anchor` 更新为
`resolution_method: "static_rva"`，`rva: "0x6E01958"`，`confidence: "medium"`
（原因见下）。随后用 `snapshot --summary` 完整跑了一遍解析链路（含
generals/cities/troops/factions 全部解析 + `validate_constants()`），
同样顺利通过，没有报错。

同时，这次验证顺带解决了第3节里"RVA 约 110MB，大得不寻常"的疑虑：实测这个
exe 的 PE `SizeOfImage` 高达 `0x098D3000`（约153MB），`0x06E01958`
（约110MB）完全落在镜像范围内。这个 exe 的镜像本身就异常大（推测是为
1100 武将/42 城池等固定大小数组预留了巨大的静态/BSS 空间），而不是这个
RVA 数值本身有问题——原先"RVA 太大不像典型 PE"的怀疑可以撤销。

**为什么最初 confidence 定为 medium**：第一次验证只是单次运行的结果，
验证清单 3.1 建议的关键区分动作——"重启游戏一次，确认这个地址/RVA 依然
成立"——当时没有做。7.7 节记录了随后补做这一步的结果。

### 7.7 重启持久性确认（同日，第二轮验证）——confidence 提升到 high

用户重启游戏并进入另一个正式对局存档后（新的进程实例，PID 从 8544 变为
18680），用**同一个** `static_rva=0x06E01958` 重新验证：

- `module_base` 依然是 `0x00400000`（没有 ASLR，符合预期）。
- **角色底表数据（不随存档变化）逐字节完全一致**：武将[0..5] 的姓氏和
  五维属性（`base_stats`）与重启前完全相同，比如武将[0]="阿會"、
  base_stats=(65,74,26,33,44)，武将[1]="韋"、base_stats=(16,19,65,73,70)。
- **随存档变化的字段确实变了，且变得合理**：同一批武将的 `faction_id`/
  `location` 在新存档里变成了不同的值（比如武将[2]从 faction_id=30 变成
  11），符合"进入了不同剧本，武将初始归属不同"的预期，不是读到垃圾。

### 7.4 文本编码发现：应为 cp950(Big5)，不是 GBK

`snapshot` 命令原样跑出来的城池名是乱码（比如城池[0]显示"粮キ"）。用
GBK/Big5/cp950 三种编码分别尝试解码城池名字段的原始字节后发现：**cp950
（Big5）能正确解码成有意义的繁体地名**，比如城池[0..9]依次是
襄平/北平/薊/南皮/平原/晉陽/鄴/北海/下邳/小沛——全部是《三国志11》里
真实存在的地名。这证实了字段的偏移/大小（`offset`/`size`）本身是正确的，
出错的只是文本解码用的编码——这完全符合"这是简体版资料，游戏是繁体版"
的预期。

已给 `offsets/pk_1.1_cn.json` 新增 `meta.text_encoding: "cp950"` 字段，
并修改 `san11agent/perception.py`（`_read_field`/`read_struct_fields`/
`parse_generals`/`parse_cities`/`parse_troops`/`parse_factions`）让
`fixed_str` 类型字段按 `OffsetsConfig.text_encoding` 解码，而不是硬编码
GBK（离线测试用的合成 dump 文件本来就是按简体 GBK 编的，所以默认值保留
`gbk` 不影响现有测试）。修完后重新跑 `snapshot`，城池名正确显示。

### 7.5 意外发现：general.name 字段内部还有子结构，现有解析不完整

验证 7.4 的过程中，用同样方法查看了几位武将的 `name` 字段完整56字节内容，
发现它不是一整段"姓名+读音"的字符串，而是三段定长子字段拼接：

- `+0x00` 起 5 字节：姓（最多2个双字节汉字 + 至少1个 `0x00` 终止/填充）
- `+0x05` 起 5 字节：名（同上）
- `+0x0A` 起约 46 字节：字/表字（courtesy name，变长，`0x00` 结尾）

实测武将[0] = 姓"阿會" + 名"喃"，姓名合并即"阿會喃"——是真实存在的南蛮
武将（孟获阵营）；武将[1] = 姓"韋" + 名"昭" + 字"弘嗣"——即东吴史学家
韋昭，字弘嗣，与史实完全吻合，强烈印证这个子结构划分是对的。

但 `san11agent/memory.py` 的 `read_fixed_str()` 只在**第一个** `0x00`
处截断，所以当时 `General.name` 实际只读出了"姓"（比如上面例子里只会显示
"阿會"、"韋"），"名"和"字"都丢失了。city.name 不受影响（城池名本身就是
单段字符串，没有这个子结构）。

**→ 已修复，见第 8.4 节。**

### 7.12 第三个独立进程实例验证（2026-08-19，用户重启游戏后）

用户再次重启游戏（新进程 PID **13364**，与此前两次的 PID 8544、18680 均不同），
在**全新启动的进程**上重新用 `static_rva=0x6E01958` 做只读验证（未做任何写内存
或键鼠输入操作）。

**身份确认**：`module_base` 仍读回 `0x00400000`（第三次确认无 ASLR），
`GAME_DATA_BASE` 解析结果仍为 `0x07201958`，与前两次完全一致。

**验证过程中的一个插曲**：第一次跑 `probe-anchor` 时校验**未通过**——
`scenario_id=-1`、`start_year=0`，武将/城池的兵力/钱/粮等动态字段全部为 0，
武将姓名字段也是空字符串。但同一次读数里，**城池名称这项静态资源表已经能
正确解出完整的42个繁体地名**（襄平/北平/薊/……/雲南，顺序与前两次完全一致）。
几秒后（游戏应该已经从标题画面加载完存档）重跑同一条命令，`probe-anchor`
和 `snapshot --summary` 均**通过**，读到完整的动态数据。

**判断**：这不是锚点失效，理由是——

1. 两次读数用的都是同一个 `GAME_DATA_BASE=0x07201958`，地址本身从未变化；
2. 校验失败那次，唯一异常的是"动态/会话数据"（剧本编号、开局年月日、
   兵力/钱/粮），"静态资源表"（城池名称数组）读数是正确且完整的——这正是
   本任务要求区分的"锚点失效"与"游戏状态不同（标题画面/未加载存档）"两种
   情况的典型信号：如果锚点本身错了，静态资源表也应该读出乱码或不完整，
   不会恰好读出42个全部正确的地名；
3. 加载完成后重跑，武将[0..5] 的姓名/base_stats、42座城池的名称，与本文件
   之前两次（PID 8544、PID 18680）记录的数值**逐字节完全一致**；
4. 这次读到的动态数据（剧本编号=0、开局184-1-1、current_xun=30、
   城池[1]兵力25418/钱680/粮51931等）与 7.7 节记录的 **PID 18680 那次的
   存档数据完全相同**——说明用户这次恢复的就是同一份存档，不是新开局，
   进一步排除了"巧合命中一块看起来合理的内存"的可能性。

**结论**：GAME_DATA_BASE 锚点（`static_rva=0x6E01958`）在**第三个独立进程
实例**上验证通过，`anchor.confidence` 维持 `high`（本次验证前已经是 high，
见 7.7 节；这次是追加的第三重独立确认，不是从 medium 首次提升）。

`pytest`：286 项全部通过（比 7.11 节记录的 266 项多 20 项，为期间新增的
测试用例，与本次验证无关）。

**给下游代码的建议**：`probe-anchor`/`snapshot` 单次校验失败不应直接当作
"锚点错误"处理——如果同时看到"动态字段为0/-1，但静态资源表读数正常"这个
组合信号，更可能是"游戏还停在标题画面/还没加载完存档"，建议轮询重试或
提示用户确认游戏状态，而不是立即报错退出。

i32值，解引用后在附近 ±0x100 字节范围内找 3600/3900，也没找到）——这
进一步支持了之前的猜测：这些字段活在一个通过指针间接访问的独立子结构
（很可能就是原资料提到但从未破解的"设施(Facility)"结构体，函数
`0047c4c0`），不是 City 数组本身线性排列能碰到的地方，也不是一步解引用
就能找到的简单指针。要彻底解决，大概率需要反汇编 `0047c4c0` 这个函数
本身（IDA 之类的工具），这超出了这次"读内存找规律"的方法能做到的范围，
如实记录为未解决，不继续盲测。

### 8.4 两个已知代码 bug 的修复（2026-08-18，用户确认后执行）

前面几节发现的问题里，有两个是**已经写进代码、会产生错误输出**的真 bug
（不是"数据缺口"）。用户确认后一并修掉。

#### bug 1：`General.name` 只读出了姓

**影响面**：实测 1100 位武将里 851 位有姓名，其中 **849 位（99%）的"名"被丢掉**
——显示成"張"而不是"張角"。这个字段一路流到
`situation_summary.py`（第172行）拼进给 LLM 的局势描述文本里，也就是说
**LLM 看到的武将名基本全是残的**，根本没法把人和历史知识对上。

**修法**：offsets 里把原来那个 56 字节的 `general.name` 拆成实机确认的三段——
`surname`(+0x04, 5) / `given_name`(+0x09, 5) / `courtesy_name`(+0x0E, 46)。
拆之前先对**全部 1100 条记录**做了边界校验（`surname[4]` 和 `given_name[9]`
是否都为 `0x00`），**零违例**，确认布局成立才动手。`General` 新增
`surname`/`given_name`/`courtesy_name` 三个字段，`name` 保持存在但语义变成
"姓+名拼接出来的完整姓名"，这样所有下游（boundary → VisibleGeneral →
situation_summary）不用改一行就自动拿到正确的名字。

`perception._general_name_parts()` 对"只声明了旧 `name` 字段"的 offsets 文件
保留了一条退路：拿 `name` 当姓、名和字留空。退化行为是"信息不全"，不是
"编造"或"报错"。

**未做的最终确认**：修完时游戏已经关掉，所以没能再跑一次真实进程做端到端
核对。字节布局本身是在游戏还开着时用全量 1100 条记录验证过的，组合逻辑有
单元测试覆盖，但"跑一次 snapshot 看看 849 个名字是不是真的补全了"这一步
**没有做**，留给下次开游戏时顺手确认。

#### bug 2：M2 的"是不是我自己的"判断，前提本身不成立

**影响面**：`boundary.py` 用 `xxx.faction_id == player_faction_id` 判断归属，
而 7.9/7.10 节证明这两个字段根本不是稳定的势力ID（驻守武将的该字段等于
所在城池 index，部队的该字段绝大多数是 -1，城池的该字段至今 unknown 恒为
None）。也就是说这个比较在真实内存下**几乎永远为假**——玩家自己的武将、
自己的首都、自己的部队全都会被当成"非己方"。这不是"字段没验证所以保守
拒绝"的安全退化，是判断依据本身错了。

**修法**：新增 `san11agent/faction_resolve.py`，用 7.11 节验证过的
`force_id -> Force.faction_id` 链路解析归属：

| 路径 | 验证状态 |
|---|---|
| `of_city()` | ✅ 已验证（12 座城池，全部给出符合剧本的历史归属） |
| `of_general()` | ✅ 已验证（9 位武将，含韓忠 force_id=6 与花名册"2張角"吻合） |
| `of_troop()` | ⚠ **未验证**——Troop 没有 force_id，只能经主将绕两跳，这条路没在实机上核对过 |

解析不出来一律返回 `None`，与 `player_faction_id` 比较必然为假，**自动
fail-closed**（宁可自己人也看不全，也不把敌方误判成己方而泄漏信息）。

另外把 `VisibleXxx.faction_id` 改成装**解析后**的势力ID 而不是原始字段——
这样 `legal_actions.py` / `situation_summary.py` 里现有的
`faction_id == player_faction_id` 判断自动就对了，不用逐个改调用点，也避免
了"多处各自解析、可能不一致"。

**回归测试**：光让测试通过是不够的——原来的 fixture 里 raw `faction_id` 恰好
等于解析后的势力ID，所以它证明不了"确实用了 resolver"。新增了一组照搬实机
形态的测试（武将 `faction_id` 装城池 index、城池 `faction_id` 为 None、部队
`faction_id` 为 -1），并**实际验证过：把代码退回旧逻辑，这组测试会挂 3 个**。
另有一个测试锁住"军团表缺失时必须 fail-closed 而不是 fail-open"。
