# 执行层调研与设计取舍报告（M3）

> 本文档记录 M3（执行层最小链路脚手架）依赖、但目前**无法从真实游戏内存/窗口
> 里确定**的信息，以及这次新写的执行逻辑里包含哪些**未经真实游戏验证的设计
> 假设**。做法与 docs/offset_research.md（M1）、docs/visibility_research.md
> （M2）一致：找不到依据的地方明确标 unknown 并列出来，不猜测填值；新写的
> 代码逻辑里如果包含"猜"的成分（比如坐标换算公式），也明确写出来，不假装
> 它是已验证的事实。

## 0. 本次范围

用户明确要求：本次**不接触真实游戏**（游戏当前无法运行——用户机器锁屏、
人在远程，且 M1 的 GAME_DATA_BASE 锚点仍未解决），只搭建可离线测试的执行层
基础设施（InputBackend 抽象、坐标计算、轮询/超时/重试机制、归位例程、动作
日志），用假后端 + 假内存 + 可注入时钟完全离线验证。所以本文档里列出的
"缺口"，没有一项是这次尝试去解决又没解决的——而是这次的工作范围本来就不
包含"去定位这些内存字段/测量这些屏幕坐标"，全部是新识别、新记录的缺口。

## 1. 新增的内存缺口

M3 执行链路（"读城池坐标 -> 滚动地图 -> 点击 -> 轮询确认选中状态变更"）
额外依赖两组在 M1/M2 阶段都不需要的内存字段，这次为它们在
`offsets/pk_1.1_cn.json` 里新增了 `camera` 和 `selection` 两个 struct，
和 M1 其余未知字段一样标记 `unknown: true`：

1. **camera.offset_x / offset_y / zoom_level**（地图摄像机偏移/缩放）——
   `map_projection.py` 需要它才能把地图格子坐标换算成屏幕坐标。311MemoryResearch
   资料库里没有检索到跟"摄像机/地图滚动/缩放"相关的字段（这次也没有重新
   专门去查——不在本次范围内），需要之后专门定位，比如对比拖动/滚动地图
   前后的内存快照差异。
2. **selection.selected_city_index**（当前选中/高亮的城池 index）——
   `execution.py` 用它轮询确认"点击城池"这个动作是否生效。同样没有找到
   对应字段，需要之后对比点击不同城池前后的内存快照差异来定位。

这两组字段解决之前，`CitySelector.select_city()` 在真实进程场景下会在
`project_tile_to_client()`（camera 未知）处直接抛出 `MapProjectionError`，
不会用编出来的坐标点到游戏里的未知位置——这是刻意的，和 M1/M2 的一贯做法
一致。

## 2. 界面坐标缺口：ui_layout 完全没有测量数据

新增了 `ui_layout/` 目录（跟 `offsets/` 平行，但存的是屏幕像素坐标而不是
内存偏移，来源是"实际测量运行中的游戏窗口"而不是"逆向内存资料"，两者验证
方式不同故意分开成两套文件格式）。目前 `ui_layout/pk_1.1_cn.json` 里唯一的
元素 `map_viewport`（地图显示区域的矩形范围 + 每格像素尺寸）全部是
`unknown: true`——游戏无法运行，完全没有任何截图或测量数据。等游戏能跑
起来后，需要实际测量（截图量坐标，或用 Spy++/AutoIt Window Info 之类工具）
填入。

## 3. 这次新写的代码里包含的、未经验证的设计假设

以下几条不是"内存资料里没找到的事实"，而是这次为了让执行层脚手架能跑起来
自己设计的逻辑，**其正确性完全没有被真实游戏验证过**，游戏能跑之后需要
逐条确认或修正：

1. **地图坐标换算公式假设"每格子独立线性缩放"，不是等距(isometric)投影**
   （`map_projection.py` `project_tile_to_client()`）：`client_x` 只依赖
   `tile.x`、`client_y` 只依赖 `tile.y`。**2026-08-19 用户截图+澄清后确认
   这个假设有问题**：底层瓦片坐标系本身是正交的（旋转相机视角能让格子
   变成规则正方形，证明数据层面就是普通行/列整数，不是菱形/六边形坐标），
   但**默认相机角度下屏幕渲染是等距投影**——从截图看格子在屏幕上是斜向
   排列的菱形，意味着 `client_x`/`client_y` 需要同时依赖 `tile.x` 和
   `tile.y`（标准等距公式形如 `screen_x = origin_x + (tile.x - tile.y) *
   半格宽`，`screen_y = origin_y + (tile.x + tile.y) * 半格高`，具体符号/
   参数仍需实测）。现有公式尚未按这个结论重写（不在本次改动范围，需要先
   有 `map_viewport` 的真实像素测量数据才好验证新公式对不对），但**这条
   假设已经从"需要你确认"降级为"已知有问题、需要重写"**。见下方7.6节。
   一个有价值的备选思路（用户提供）：游戏似乎支持切换到"正方形"视角
   （见7.6节），如果 Execute 层能在点地图前先切到那个角度，现有的简单
   公式反而可能直接可用，不需要实现等距变换——这个可能性本次没有验证。
2. **zoom_level 的数值语义假设为线性缩放比例**（除以100得到缩放系数）：
   也可能是索引进一张预设缩放挡位表（比如只有5级缩放），需要实机确认。
3. **camera.offset_x/offset_y 的单位假设是"格子"**，不是"像素"：如果实际
   是像素单位，换算公式要相应调整（不再乘以格子像素尺寸）。
4. ~~**地图滚动的具体输入方式假设是方向键**~~ **2026-08-19 已确认并修正**：
   用户直接确认左右方向键在这个游戏里是**旋转相机视角**，不是平移地图；
   真正平移靠的是把鼠标移到屏幕边缘、游戏自动向那个方向滚动。之前用方向键
   平移地图的实现是一个**已确认的错误**（不再是"未经验证的假设"）——如果
   真跑在 `--live` 模式下，点击流程会先把相机转乱，而不是把目标格子挪进
   视野。已改成移动鼠标悬停在 `viewport` 对应方向的边缘（`execution.py`
   `_edge_point_for_direction()`），`CitySelector`/`ActionMenuExecutor`
   共用的 `reveal_tile()` 函数、以及 `tests/test_execution.py`/
   `tests/test_menu_execution.py` 里对应的测试都已同步更新，全部测试通过。
   见下方7.6节。
5. **归位例程的"已知界面"校验能力有上限**（`execution.py` `_home()`）：
   归位只能做到"连续发送 N 次 Esc"，无法真正验证退回到了哪个界面——因为
   `GlobalState.phase`（游戏阶段标志位，M1 就已知未知，见
   docs/offset_research.md 4.5节）仍然是 unknown。等这个字段解决后，归位
   例程里应该补一次"读 phase 确认确实回到了预期界面"的校验，现在这一步
   是空的。
6. **窗口查找启发式**（`window.py` `_find_main_window_for_pid()`）：用
   "属于目标 pid、可见、标题非空"的第一个顶层窗口作为游戏主窗口，没有针对
   San11WPK.exe 实机验证过（截至2026-08-18仍未验证，见 docs/offset_research.md 第7节）。如果游戏窗口是无边框全屏、或标题为空，这个启发
   式会找不到窗口。
7. **SendInput 是否会被游戏感知，未经验证**（`input_backend.py`）：
   `SendInputBackend` 注入的是标准 Win32 输入消息。如果 San11WPK.exe 用
   DirectInput 或 Raw Input 直接轮询硬件状态而不是从系统消息队列取输入，
   SendInput 可能完全不起作用。备选方案是 pydirectinput 或虚拟 HID 驱动，
   需要你确认后再切换实现，这次没有做。
8. **MapProjectionError 和 UILayoutError 在"是否会被重试"上处理不同**
   （`execution.py` `select_city()`）：`camera` 字段 unknown 触发的
   `MapProjectionError`，和"滚动多次仍找不到目标格子"的 `MapProjectionError`，
   目前被同一个 `except` 分支捕获、一样会被归位重试 `max_retries` 次再放弃；
   但 `UILayoutError`（ui_layout 元素 unknown）不会被捕获，会直接从
   `select_city()` 抛出，不重试。这个区分背后的意图是"配置缺失重试也没用"，
   但严格来说 camera 字段 unknown 同样是配置缺失，目前却被归进"可重试"的
   分支里——这是可以商榷的设计取舍，见下方"需要你确认的问题"第3条。

## 4. 已经做到、可以离线验证的部分

- 轮询/超时/重试机制（`polling.py`）：可注入 Clock，测试完全不真的等待。
- 完整动作日志（`action_log.py`）：时间/意图/参数/结果/状态差异，`ActionLog`
  用的时钟和轮询用的是同一个，时间戳可以互相对照。
- InputBackend 抽象两套实现（`input_backend.py`）：`FakeInputBackend` 支持
  `on_click`/`on_key_press` 回调，可以在测试里模拟"游戏对输入做出反应"。
- 可写的离线内存镜像 `MutableMemoryReader`（`memory.py`）：仅供测试模拟内存
  值随"游戏反应"变化，明确不代表、也不应该被理解为本项目具备写真实游戏
  进程内存的能力——真实进程场景下依然只做 `ReadProcessMemory`（只读），
  游戏交互只通过键鼠输入进行。
- `CitySelector` 完整链路（`execution.py`）在假后端+假内存+可控时钟下的
  全部关键分支：目标已在视野内直接点击成功、目标在视野外先滚动再点击成功、
  点击未生效触发归位重试、重试耗尽后失败、camera/ui_layout 配置缺失时的
  报错行为区别，见 `tests/test_execution.py`。

1. `camera.offset_x/offset_y/zoom_level`、`selection.selected_city_index`
   这两组内存字段完全没有定位。你是否有额外资料（CE 表、SCP 插件源码）能
   提供，或者打算之后一起对着运行中的游戏做内存搜索（对比拖动地图/点击

2. `ui_layout/pk_1.1_cn.json` 里 `map_viewport` 的屏幕坐标完全没有测量。
   游戏能运行后，是打算你截图告诉我坐标，还是我们一起用某个工具（比如
   AutoIt Window Info）现场量？
3. 第3节列出的8条设计假设，尤其是：
   - ~~地图网格是正交还是菱形/错位~~ **2026-08-19 已确认**：数据层面正交，
     默认视角是等距投影，见第7.6节，`map_projection.py` 公式仍待重写；
   - ~~地图滚动到底是方向键、鼠标拖拽、还是边缘滚动~~ **2026-08-19 已确认

4. 归位例程目前只能"发 Esc"，无法校验是否真的回到了已知界面——这个限制

   docs/offset_research.md 第5节第5条）。是否需要提高这个缺口的优先级？

## 6. M3/M4 Execute 扩展：菜单执行（2026-08-19，`san11agent/menu_execution.py`）

新增 `ActionMenuExecutor`，把 M4 `enumerate_legal_actions()` 产出的
`Action` 对象转换成"双击城池弹出指令菜单 -> 点顶层菜单项 -> 点二级子菜单
项"这段键鼠序列，是 `CitySelector`（只做到"点城池确认选中"）往下的延伸。

**跟 M1~M4 的关系**：菜单结构（哪个 `ActionKind` 对应哪个顶层菜单/第几项
子菜单）直接取自 `docs/offset_research.md` 第8.1节——那是实机截图确认过
的真实菜单顺序，不是这次编的；`DiplomacyAction`/`StratagemAction` 的子
类型下标则动态从 `rules/domestic_actions_pk_1.1_cn.json` 里 `sub_types`
字典的插入顺序算出，不额外维护一份可能和 rules 文件走岔的下标表。

**复用 `CitySelector` 的滚动逻辑**：把"把目标格子滚进视野"这段代码从
`CitySelector._reveal()` 抽成模块级函数 `execution.reveal_tile()`，两个
类共用，没有重复维护同一段地图滚动逻辑（这是这次唯一动到 `execution.py`
既有代码的地方，`tests/test_execution.py` 全部7项测试重构后原样通过，
确认行为没变）。

**这条链路完全无法自我验证——不是简化，是当前已知信息量的极限**：跟
`CitySelector` 能靠 `selection.selected_city_index` 轮询确认点击生效不同，
"当前哪个菜单打开着"/"哪一项被选中"没有任何已知内存字段能读到（根源是
`GlobalState.phase` 仍然 unknown，M1 老缺口）。所以 `ActionMenuExecutor`
里没有轮询、没有超时、也没有重试——每一步都只是"发送输入 + 记日志"。

**新增的界面坐标缺口**：`ui_layout/pk_1.1_cn.json` 新增 `city_top_menu`/
`city_submenu` 两个元素，跟 `map_viewport` 一样全部 `unknown: true`；
`UIElement` 新增 `item_height`/`item_count` 两个字段专供菜单类元素使用
（普通元素留 `None`），坐标未知时 `require_known()` 直接抛 `UILayoutError`，
不会点到编出来的位置。

**这次明确没有实现的部分**（不是遗漏，是这次的范围边界，见模块文档）：

1. `BuildFacilityAction` 选具体设施类型——「開發」界面是19个设施图标的
   网格（见第8.3节的「設施數」「空地」等截图描述），不是垂直列表。
2. `DiplomacyAction`/`StratagemAction` 选具体目标势力/城池——点完子类型
   后大概率还有一层选目标的界面，完全没有资料参考。
3. 多个指令流程末尾的"決定"确认按钮——这次对话记录里的出征操作就卡在
   了这一步附近。

对以上三类，`execute_action()` 会在完成能做的两级菜单点击后，明确抛出
`FurtherStepsNotImplementedError`，不会假装动作已经完整执行。

**新增的、未经验证的设计假设**：双击的实现是连续调用两次
`InputBackend.click()`（`InputBackend` 没有专门的 `double_click()` 原语），
真实系统双击判定的时间间隔没有建模——跟已有的"方向键滚动地图""zoom_level
线性缩放"等假设是同一性质，见第3节。

**测试**：`tests/test_menu_execution.py`（14项）离线覆盖 `resolve_menu_path()`
对6种 `ActionKind` 的下标计算（含 diplomacy/stratagem 按 rules 顺序动态
解析、未知子类型报错）、`open_city_menu()` 的归位/滚动/双击序列、
`execute_action()` 的点击坐标计算（验证 anchor + 偏移 + index*item_height
的算法）、终止型动作正常返回 vs 需要更深步骤的动作抛
`FurtherStepsNotImplementedError`、ui_layout 元素未知/下标越界的报错行为。

## 7. 2026-08-19 尝试用全内存扫描定位 `phase`/`camera`/`selection`——工具可用，三个字段均未能稳定定位

用户当天在游戏内出征、切菜单时，趁着游戏在跑，做了一次专门定位这三个
长期 unknown 字段的实机尝试。第一步先用已有的 `mem-dump`/`mem-diff`
（只对比 `GAME_DATA_BASE` 附近一小段区域）测试菜单开合/拖地图前后，
**该区域内一个字节都没变化**——说明这几个字段大概率不在"游戏世界数据"
这个结构体附近，而是进程里完全独立的另一块内存（比如引擎自己的
UI/摄像机管理器对象）。

### 7.1 新增全内存扫描工具 `san11agent/mem_scan.py`（辅助工具三）

为此新增了枚举+对比整个进程私有内存（`VirtualQueryEx` 枚举
`MEM_PRIVATE`/`MEM_COMMIT`/可读区域，默认排除 `MEM_IMAGE` 镜像区域）的
工具，CLI 新增 `full-mem-dump`/`full-mem-diff`/`full-mem-toggle` 三个
子命令。实测该进程私有内存约 213MB、298 个区域，单次抓取约18秒，diff
约1.5秒（"按4096字节块跳过"算法，块内容相同直接跳过，只有块不同才逐
字节定位）。另外实现了 `find_toggled_spans()`——给定"操作前/操作中/
操作后"三份快照，只挑"前后相同、中间不同"的字节，比单纯两两 diff 更能
排除背景噪音（详见下文，idle 状态几秒内背景噪音就有4000+处）。这套
工具本身是扎实的基础设施，问题不在工具，在于三次实机尝试都没能靠它
稳定定位到目标字段，记录如下，避免以后重复走同样的弯路。

### 7.2 `global.phase`：两轮候选均未通过独立验证

**第一轮**（菜单开合，"操作中"快照在双击瞬间抓取）：`find_toggled_spans()`
从4151处原始噪音里筛出20处候选，其中三处是很干净的 1↔0 布尔型开关
（`0x0BAEE8B0`/`0x0BAEE8F0`/`0x0BAEFC34`，后两者间距恰好0x1184字节，
疑似重复结构数组）。**独立验证时失败**：菜单重新打开、直接实时读取这些
地址，读到的全是"空闲"时的值，一个都没有再次翻转——说明第一轮的信号
更可能是双击瞬间的一次性点击/动画处理副作用，不是"菜单是否打开"这种
持续状态。

**第二轮**（同样是菜单开合，但让菜单打开后停留约10秒再抓"操作中"快照，
排除点击瞬间干扰）：候选骤降到3处，其中 `0x1193C1A1`/`0x1193C1A5`（相差
4字节）呈现出很像状态码的模式（空闲时 `0x00`/`0x20`，菜单打开时
`0x10`/`0x30`，恰好都是加了同一个 bit）。**独立验证同样失败**：随后
用户确认游戏确实处于空闲状态，但实时读取这两个地址读到的却是"菜单打开"
的值——跟真实状态对不上，说明这两个字节被某种和"城池菜单开合"无关的
因素驱动，不是稳定的 phase 标志位。

结论：两轮方法不同（是否等待、候选数量差两个数量级）但结果一致——
**没有找到能稳定复现的 `phase` 信号**。真正的 `phase` 字段（如果确实
以单一字节/字段形式存在）没能靠"开关一次菜单、前后对比"这种粒度的
操作定位到，需要更精细的手段（比如调试器断点挂在切换界面的函数上，
或者从反汇编入手），本项目目前的工具做不到这个精细度。

### 7.3 `camera.offset_x/offset_y`：拖地图触发的内存变化规模远超预期，噪音淹没了信号

用三次同方向连续拖动（A→B→C）做交叉验证（只看两次过渡里都变化、且
变化幅度小、方向一致的候选）。**背景噪音规模远超菜单实验**：A→B 有
109万处字节变化，B→C 有98万处，即使只看4字节（i32）大小的交集也有
5.6万处——按"两次变化同号、幅度≤2000"过滤后，**候选数为0**。

判断：拖地图会触发大量地图渲染相关的内存活动（贴图/瓦片缓存/小地图
刷新等），这些活动产生的变化量比摄像机偏移这类单一字段的信号大好几个
数量级，简单的"前后对比+方向过滤"这套方法在这个操作上完全不够用，
需要更有针对性的排除手段（比如先排除明显是大块连续贴图数据的区域，
或者用调试器直接找访问摄像机坐标的具体指令地址）。

### 7.4 `selection.selected_city_index`：唯一候选未能跨多个城池复现

单击城池不像双击开菜单/拖地图那样触发大量渲染，`find_toggled_spans()`
用"襄陽→江陵→襄陽"三点采样时**只筛出1处候选**（`0x1C1FF160`，襄陽=172，
江陵=156），初看很有希望。但独立验证时：又单击了江夏（跟襄陽、江陵都
不同的第三座城），实时读到的值是172——**跟襄陽相同，而不是一个新的
第三个值**。如果这个字节真是"当前选中城池的index"，三座不同的城应该
读到三个不同的值。这个结果不能证伪"它是某种跟选中城池间接相关的字段"，
但足以证伪"它直接等于 city.index"这个最初的猜测，且样本量（只测了3座
城）不足以下进一步结论。

### 7.5 小结与后续建议

三个字段、三种不同的操作（菜单开合/拖地图/点城池），三种不同的排噪方法
（toggle检测/方向一致性过滤/多次独立验证），全部尝试后**没有一个稳定
定位成功**。这不是工具或方法论层面的失败——`mem_scan.py` 提供的枚举/
diff/toggle 三个原语都经过实测证明能正常工作、能有效把候选范围从百万级
压缩到个位数——而是"用几次粗粒度的键鼠操作、对比前后内存快照"这种手段，
对这三个具体字段来说分辨率不够。可能需要的后续方向（本次都没有做）：
1. **调试器断点/反汇编**：在切换界面、更新摄像机、处理点击的具体函数
   上挂断点，直接看函数访问了哪个地址，比"猜哪块内存变了"精确得多，
   但需要用到本项目目前完全没有涉及的逆向工程工具链。
2. **更大样本量的交叉验证**：比如 `selection` 如果测5~6座不同的城池，
   而不是3座，可能能更可靠地排除/确认候选。
3. **接受这几个字段短期内定位不了**，`CitySelector`/`ActionMenuExecutor`
   在真实游戏场景下继续保持"配置缺失就报错，不猜测坐标"的现状。

`mem_scan.py` 的三个新 CLI 子命令和核心算法（区域过滤、按块跳过 diff、
toggle 检测）本身有18项离线单元测试覆盖，跟本次实机尝试成功与否无关，
是这次真正沉淀下来的、可复用的基础设施。

**副产品，比本次要验证的问题更有价值**：查 `state.cities`（42座）按名字

### 7.9 2026-08-19 追加两个方法论层面的教训（`selection` 第5次尝试 + 调试器初次尝试）

**教训①：全内存 toggle 对比方法本身有速度上限，不只是"点错了"的问题**——
怀疑之前 `selection` 的候选反复失败可能是"单击城池同时触发了选中+弹出
菜单两件事，信号被混在一起"，于是改成**只悬停不点击**（用户确认过悬停
本身就会选中/高亮，不需要点击）重新测了一轮：襄陽idle基准 -> 悬停「鄴」
（非己方城池，太守韓馥）-> 移开鼠标回到idle。结果 `find_toggled_spans()`
筛出 **0 个候选**（比之前任何一轮都干净，反而说明问题更大）。原因分析：
`full-mem-dump` 单次抓取约18~20秒，三次快照抓完（含中间等待用户操作的
时间）实际跨度可能长达一两分钟——这段时间里游戏后台本身的动画/音效/
渲染状态持续变化，导致"操作前"和"操作后"这两个本该完全一致的空闲基准
状态，在200+MB范围内几乎不可能有哪怕一个字节恰好在两次抓取里都完全
一致，"变了又变回去"这个筛选条件因此把真实信号也一起过滤没了。**这是
方法本身在当前抓取速度下的天花板，不是操作方式的问题**——不管点击还是
悬停，只要三次快照之间隔着几十秒，都会撞到这个限制。

**教训②：调试器侵入式附加（`cdb -p PID`）会在附加的瞬间就暂停游戏全部
线程，不是等断点命中才暂停**——按用户要求安装了 WinDbg（`winget install
Microsoft.WinDbg`，含 `cdb.exe` 命令行调试器）并验证过非侵入式附加
（`-pv`）能正常连接、读到正确的模块基址（`0x00400000`）和镜像大小
（`0x098D3000`，与之前 PE 头信息完全一致）。但随后尝试"设读断点 + 附加
+ 等待命中 + 恢复运行"这个组合操作时，误判了侵入式附加（`-p PID` 不带
`-v`）的行为——Windows 在侵入式附加的**那一刻**就会让目标进程停在一个
初始断点（`ntdll!DbgBreakPoint`），不是等到我设的读断点被触发才暂停；
后续用来"读调用栈+寄存器再恢复运行"的命令串（`k; r; bc *; g; qd`）没能
顺利执行完（推测卡在 `k` 命令的符号解析上，尝试联网访问微软符号服务器
拖慢或卡住了），导致游戏停留在暂停状态，用户被迫强制重启游戏，丢失了
那一局的（少量）未存档进度。已确认清理了残留的 `cdb.exe` 进程，新的
游戏进程恢复正常。**这不是"调试器工具不能用"，是这次操作的命令编排
有问题**——正确做法应该是先用一次"接管后立刻 `g` 恢复运行"的空操作
单独验证"附加不会卡住"，再叠加断点逻辑，而不是把两步一次性合并。
这次事故后本次会话不再尝试任何会让游戏线程暂停的调试器操作。

**给下次的建议**：如果以后要用调试器真正推进这几个字段，(a) 附加前
务必先备份存档/确保可以随时接受游戏被强制重启；(b) 第一次连接后先
单独测试"附加→立刻 `g`→干净分离"这个最小闭环，确认不会卡住，再加
断点逻辑；(c) 用 `.symfix+`/清空符号路径或加 `-sflags` 避免 `k` 命令
触发网络符号解析拖慢关键的"恢复运行"步骤；(d) 优先用 TTD（Time Travel
Debugging，`cdb`/`WinDbg` 均自带 `TTD.exe`）录制一小段执行轨迹、事后
离线分析，而不是用会实时暂停进程的传统断点——录制过程游戏正常运行，
不会被"断点卡住忘了恢复"这类风险影响，这次没有尝试，是更安全的后续
方向。

### 7.6 2026-08-19 用户直接确认两条设计假设，其中一条是已实现代码的确认错误——已修正

`phase`/`camera`/`selection` 三个字段的内存扫描没有成果之后，转向"不需要
猜内存地址、纯观察/纯问答就能确认"的设计假设，一次性拿到了两条有实际
代码影响的结论：

**① 地图网格：数据层面正交，但默认视角是等距(isometric)投影**——见第3节
第1条修正后的完整说明。用户的关键澄清是"旋转视角能让格子变成正方形"，
这把"底层坐标系"和"屏幕渲染投影"两件事分开了：本文档最初把"截图看起来
是菱形"直接当成"坐标系是菱形"，是把两者混为一谈的错误推理，被用户当场
指出并纠正。这次没有改动 `map_projection.py` 的代码（重写等距公式前
需要先有 `map_viewport` 的真实像素测量数据，本次没有），只更新了文档结论。

**② 地图平移方式：确认是鼠标停靠屏幕边缘，方向键是旋转相机——已修正代码**：
用户直接回答"按左右方向键会旋转视角（格子变正方形），平移地图是把鼠标
移到屏幕边界、自动平移"。这条不是"文档记录留给以后"级别的发现，是
**当前已实现代码的一个确认错误**——`execution.py` 的 `reveal_tile()`
（`CitySelector`/`ActionMenuExecutor` 共用）之前用 `key_press(VK_LEFT/
RIGHT/UP/DOWN)` 去平移地图，如果这段代码真跑在 `--live` 模式下，会把
相机角度转乱，而不是把目标格子挪进视野——是方向性错误，不是精度不够。

**已做的修正**：
- `execution.py`：新增 `_edge_point_for_direction()`，把"往哪个方向平移"
  翻译成 `viewport` 矩形对应边缘的一个客户区坐标点；`reveal_tile()` 改成
  `window.client_to_screen()` 换算屏幕坐标后 `input_backend.move_mouse()`
  悬停在那个点，不再调用 `key_press()`；轮询逻辑本身不变（仍然是"移过去
  -> 等一段间隔 -> 看摄像机变没变"）。`reveal_tile()` 新增 `window`
  形参，`CitySelector`/`menu_execution.ActionMenuExecutor` 两处调用点
  都已同步传入。
- `input_backend.py`：`FakeInputBackend` 新增 `on_move_mouse` 回调（原来
  只有 `on_click`/`on_key_press`），供测试模拟"鼠标悬停在边缘触发平移"。
- `action_log` 的 `intent` 从 `"scroll_map"` 改名为 `"pan_map"`，`日志
  detail` 措辞也从"滚动"改成"平移"，跟实际操作语义对齐。
- `tests/test_execution.py`/`tests/test_menu_execution.py`：原来用
  `on_key_press`+`VK_RIGHT` 模拟平移触发的测试，改用 `on_move_mouse`+
  精确边缘坐标断言（`viewport` x=100,y=50,width=400,height=300 时，右
  边缘悬停点算出来是 `(497, 200)`），测试语义和实际实现路径完全对齐。
  全部 324 项测试通过（含这次改动涉及的两处重命名测试）。

**仍未做、需要之后补的**：`_edge_point_for_direction()` 本身的具体像素
参数（悬停点离边界多近才会触发平移、平移速度、悬停多久算"触发"）完全
没有实机数据，`_EDGE_MARGIN = 2` 只是一个凑数的默认值；真实平移触发的
判定逻辑（比如可能需要连续多帧悬停在边缘才触发，不是移过去一瞬间就有
效）也未经验证。等 `camera` 字段和 `map_viewport` 坐标解决后，需要用
真实游戏验证这一整段代码是否真的能触发平移。

### 7.10 2026-08-19 城池菜单像素坐标测量：`GetCursorPos`+`ScreenToClient` 协议零风险拿到 `city_top_menu`/`city_submenu`

### 7.12 2026-08-19 `map_projection.py` 重写成等距菱形变换

7.6节记录的"地图默认渲染是等距投影"这个结论，当时只改了文档、代码没跟上
（缺 `map_viewport.tile_width/tile_height` 真实数据）。7.10节测出
`tile_width=184`/`tile_height=135` 之后，这次把公式正式重写：

- 原来的"正交网格 + 统一缩放"公式 `client = viewport.xy + (tile - offset)
  * tile_size * zoom` 换成等距菱形变换：`half_w`/`half_h` 取 tile 尺寸的
  一半，`client_x = 视口中心x + (dx-dy)*half_w*zoom`、`client_y = 视口中心y
  + (dx+dy)*half_h*zoom`，`dx=tile.x-offset.x`、`dy=tile.y-offset.y`。
- **新引入了一条之前没有的假设**：`camera.offset` 对应的格子投影到**视口
  正中心**，而不是像旧公式那样投影到视口左上角——因为"摄像机偏移=屏幕
  中心对着哪个格子"是更符合直觉的游戏摄像机通行约定，但这纯粹是设计选择，
  camera 字段本身还没定位到内存里，无法回放验证这条假设对不对。
- **方向约定也没验证**：这次测量只量了单个格子自己的四个顶点（证实"这是
  菱形"），没有测相邻两格的中心点，所以"tile.x 增大对应屏幕右下、tile.y
  增大对应屏幕左下"这个符号约定是猜的，不是实测结论。
- `execution.py` 的 `_pick_scroll_direction()` 原来直接拿
  `target_tile.x/y` 跟 `camera.offset_x/offset_y` 逐轴比较来决定平移
  方向（正交网格假设），改成跟 `project_tile_to_client()` 同一套
  `(dx-dy, dx+dy)` 关系判断屏幕方向。
- 同步更新了 `tests/test_map_projection.py`（7个用例全部按新公式重算
  期望值）、`tests/test_execution.py`/`tests/test_menu_execution.py`
  里几处硬编码了旧公式坐标的用例（`TileCoord(5,5)` 的预期落点从
  `(200,150)` 改成 `(300,300)`；"目标在视野外靠平移进入视野"的用例把
  目标格子从 `(30,5)` 改成 `(30,y=offset_y)` 以避免等距变换下"改一个轴
  两个屏幕方向一起变"的耦合，让测试场景仍然只需要模拟一次单方向平移）。
  全部333项测试通过。
- **这次改动不依赖真实游戏、纯离线代码/测试工作**——公式对不对，仍然要
  等 `camera.offset_x/offset_y/zoom_level` 三个字段被定位到内存里之后，
  才能真正拿真实点击验证。

### 7.13 2026-08-20 `selection`/`action_points` 第7-8次尝试：TTD today 失效 + 内存扫描新技巧（贴图数据是主要干扰源）

用户第二天回来后想再试 `selection.selected_city_index`，认为上次失败是自己
操作问题，实际排查发现是**工具链本身的问题**：

- **TTD `-module` 参数今天失效了**：同样的录制命令（`-module San11WPK.exe`），
  昨晚能录到330~680MB，今天连续4次录制都只有精确的4194304字节（4MB整数），
  时间戳/操作强度都不影响这个数字。做了个不加模块过滤的2秒诊断录制，
  直接录到713MB——证明 TTD 本身工作正常，问题具体是 `-module`
  过滤条件今天没生效。中途还排查过"UAC弹窗抢焦点"（提权console窗口挡住
  游戏，用户第一次点击其实点在了console上）这个真实存在但不是唯一原因的
  问题，加了 `-WindowStyle Hidden` 后console不再挡屏，但录制大小依然是
  4MB，排除了这个假设。最终诊断结论：`-module` 过滤本身坏了，不是用户
  操作或焦点问题。用户决定放弃 TTD，改回最原始的内存快照对比方法。

- **多城池DWORD交叉验证：交集为0**。鄴(6)/南皮(3)/小沛(9)三座城池分别做
  "选中前→选中后→取消选中"三连拍，找"精确变成目标值、又精确变回原值"的
  4字节对齐候选。单独看鄴(6)有1046个候选、小沛(9)有268个、南皮(3)有643个，
  但南皮和小沛两组候选**交集为0**——没有任何地址在两次独立实验里都精确
  命中各自城池的编号，说明这个字段要么不是4字节对齐的裸下标，要么每次
  选中都分配到不同的堆地址（这样交叉验证的前提就不成立）。

- **换1/2字节宽度重新搜（复用同一批快照数据）**：1字节宽度下鄴/小沛/
  南皮实验之间出现了15个交集地址，一度以为有突破，但**展开上下文后发现
  是假阳性**——这15个地址里好几个的周围字节内容几乎逐字节相同
  （`4b78050000000500097800000002000011`），却分布在四五个完全不同的
  内存区域（0x158xxxxx/0x230xxxxx/0x269xxxxx/0x278xxxxx），是某种被
  复制了多份的固定资源（推测是图标/字体缓存），不是"各自城池独立更新的
  选中状态"，纯属数值巧合碰撞。2字节宽度交集为0。

- **新方法论：用画面上实际显示的数值做定向搜索，但撞上了"贴图数据"这个
  之前没意识到的重大干扰源**。截图确认了「開發」界面显示 `行動力 20/255`、
  `資金 200/8785`、`空地 15/15` 等具体数值。搜索"资金=8785"（i32，理论上
  比小整数更稀有）在操作前后都稳定存在的地址只有2个，但**两个都是贴图/
  头像像素数据**——用十六进制展开上下文后能清楚看到渐变色、大片
  `ff ff ff ff`（alpha通道）等图片特征，8785只是恰好等于某几个连续像素
  字节拼出来的数值，跟资金毫无关系。这是本次最重要的方法论教训：**这
  个游戏在内存里常驻大量贴图/图标/头像的原始像素数据，是这类"搜具体
  数值"方法此前从未遇到过的强干扰源**，比背景噪音更难排除（背景噪音
  好歹会随时间变化，贴图数据在两次快照之间是完全稳定不变的，天然能
  通过"操作前后一致"这类过滤条件）。

- **摸索出一个新的过滤技巧：稀疏度过滤（可能对以后有用）**。真实的游戏
  结构体数据大片是0字节填充，贴图/像素数据几乎不会连续为0——用"候选点
  周围32字节窗口里0字节占比"这个启发式过滤"行動力=20"的35万个候选，
  占比≥60%的降到12943个，≥80%的降到3528个。这个技巧成功把候选从35万
  压到几千量级，比单纯限定字节宽度或数值稀有度更有效，值得在以后的
  搜索里复用（可以考虑做成 `mem_scan.py` 里的一个通用过滤函数）。但即使
  加上这个过滤，最后剩下的候选逐个展开上下文后，要么还是贴图头部模板
  （同一个大贴图资源区里，`14 00 00 00...`这样的固定头部字段在多个不同
  图标位置重复出现，同样会通过稀疏度过滤，因为紧跟着大片0），要么是
  实时读取验证后发现数值早就变成不合理的大数（`0x001C1188` 一度看起来
  像真结构体数据，但几分钟后单独读取实时值发现变成294676，远超
  行動力0-255的合理范围，排除）。

- **本次结论**：`selection.selected_city_index`/`city.action_points`
  依然没有定位到。跟7.9/7.11节一样，纯内存扫描类方法（不管是DWORD/byte
  toggle交叉验证，还是画面数值定向搜索）目前已经把能想到的变体基本
  用尽，共同的天花板是**贴图/图标数据在内存里跟真实游戏状态数据长得
  "同样随机"，纯靠数值巧合和局部启发式很难稳定排除**。下次如果还想
  在这条线上继续，比较有希望的方向：①把"稀疏度过滤"做成正式工具，
  ②想办法排除已知的贴图资源堆区间（比如记录几个已确认是贴图的大
  region 的地址范围，直接跳过），③修复 TTD 的 `-module` 问题后用
  TTD 的"哪条指令写了这个地址"能力做真正的写入点回溯，而不是纯粹
  猜数值。
